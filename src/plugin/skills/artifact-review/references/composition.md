# 按内容选择排版

Artifacts 渲染已写好的 Markdown，不会自动判断正文的语义并重写文档。排版选择发生在 Agent 写作阶段。以读者的问题组织内容，组件负责显露结构；不按组件数量评价文档。

## 选择依据

- 多个主题：用有意义的二级标题划分，标题直接说明这一节回答什么；一个一级标题即可，避免与元数据重复。
- 多个选项共享比较维度：用简洁表格；单元格需要长篇论证时，改用各选项的小节。窄窗口下避免过多列。
- 顺序操作：用有序列表，把动作与完成条件写在一起；待办事项才使用任务列表，不伪造完成状态。
- 关键限制或会改变决定的风险：用 NOTE、TIP、IMPORTANT、WARNING 提示框，避免把所有重点都装进框。
- 流程、依赖或分支关系：用 Mermaid 流程图；只有一两步的动作通常无需图。图中的关系必须能从材料得到支持。
- 可执行代码：代码块注明语言。命令、路径、字段用行内代码，普通中文正文不要包成代码块。
- 推导确实需要公式时使用数学公式；不要把普通指标装饰成公式。
- 长篇补充材料可以用 `<details>` 折叠；结论、必要步骤和风险不能折叠隐藏。

## 实施说明示例

以下是假设示例，演示内容如何自然使用组件；不是所有文档的固定模板。

````markdown
# 本地文档展示改进

建议在写作阶段调整内容结构，保留现有本地阅读入口。

> [!IMPORTANT]
> 文档仍留在本地。更新源文件后需重新生成阅读页。

## 两种方法适合什么情况

| 方法 | 适合的内容 | 局限 |
| --- | --- | --- |
| 分节与列表 | 说明、操作步骤 | 不直接表达复杂关系 |
| 流程图 | 多步骤与分支 | 简单内容会显得冗余 |

## 从写作到阅读

```mermaid
flowchart LR
  A[整理内容结构] --> B[保存 Markdown]
  B --> C[生成本地阅读页]
  C --> D[用户阅读]
```

## 如何验收

1. 用小标题划分不同问题，确认读者能找到主要结论。
2. 打开阅读页，确认表格与流程图可读，正文没有被裁切。
3. 修改源文件并重新展示，确认阅读页体现修改。

<details>
<summary>补充背景</summary>

这里放不影响主线阅读的解释。

</details>
````

## 展示前自查

先检查源内容：标题是否表达问题、连续段落是否混合多个主题、是否有可以更清楚地呈现为比较或步骤的信息。再检查组件：表格是否过宽、图是否只重复一句话、提示框是否太多、示例是否被明确标注。有可用预览时检查实际显示；不能验证时如实说明，不能把生成成功当作所有宿主的视觉验收。

如果只是在原文里机械增加分隔线、加粗和装饰符号，通常没有解决结构问题。也不要让渲染器自动猜测表格、流程或结论：这可能改变原文含义。
